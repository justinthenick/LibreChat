## What v0.2 fixed

The focused v0.2 correction successfully removes the hard governance failure from v0.1:

- source/proposer is separated from decision authority;
- the after-hours dispute retains `Decision Owner: Unknown` and neither stakeholder position is selected;
- overall Stage 1 readiness is explicitly `Partially Ready`;
- the contractor-onboarding, security-vetting, building-owner and Change-approval process boundary survives into downstream acceptance/assurance coverage;
- Candidate Building Access Platform automation and Candidate pilot scope remain non-committed;
- the two-business-hour objective remains a Target rather than an SLA/test gate;
- automatic revocation remains Deferred;
- evidence-retention duration remains Unknown;
- missing-field rejection/submission-prevention is explicitly *not* invented;
- manual temporary-access issuance remains the sourced fallback outcome;
- no API/protocol/storage/queue/workflow architecture or concrete test data is invented;
- end-to-end REQ/CON -> work item -> AC/constraint -> test/assurance traceability is strong.

No rubric penalties apply.

## Minor remaining issues

These are quality refinements rather than production-blocking defects:

1. The Stage 1 register still includes a generic `Decision Owner` column even though v0.2's agent contract says that column should be omitted. Crucially, the model no longer populates it with unsupported authority: confirmed/non-binding/deferred rows use N/A and unresolved items use Unknown.
2. The normal-hours negative test is a valid logical complement of the explicit `approval before issuance` boundary, but the downstream test does not explicitly label its evidence basis as `Derived boundary`.
3. The integration feasibility Spike receives a lightweight acceptance criterion even though discovery completion criteria could be represented more cleanly as a spike outcome. It does not commit the Candidate automation itself.

None of these issues causes status drift, authority invention or unsupported implementation behavior.

## Architecture decision

**Retain Composite BA Delivery Analyst v0.2 and proceed to the specialist-agent comparison.**

Benchmark 008 now demonstrates that a single-call composite can coordinate the four validated BA stages effectively. The next architectural question is therefore not whether composition works, but whether a small specialist-agent pipeline can improve reliability, auditability or stage quality enough to justify extra model calls and handoff cost.

Preferred specialist split:

1. Requirements Analyst — requirements analysis;
2. Delivery Refinement Analyst — decomposition + acceptance criteria;
3. Assurance Analyst — behavioural test / assurance derivation.

The specialist benchmark should use the same source problem or a fresh end-to-end problem with explicit handoff artifacts persisted between calls, per-stage hashes/metadata, stage token usage and end-to-end scoring. The composite v0.2 result is now the meaningful architecture control, not the no-agent baseline alone.
