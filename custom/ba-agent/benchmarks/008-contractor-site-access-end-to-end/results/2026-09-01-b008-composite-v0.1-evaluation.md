## What materially improved over baseline

The composite agent substantially improved structural discipline:

- explicit Stage 1 -> 2 -> 3 -> 4 handoffs;
- the after-hours dispute remained unresolved and Decision Owner for that dispute stayed Unknown;
- Candidate automation/pilot, Target response time, Deferred revocation and Unknown retention did not become committed downstream functionality;
- end-to-end REQ -> delivery -> AC -> test traceability was much stronger;
- no concrete API/protocol/storage architecture was committed;
- output duplication was modest despite the additional stage controls.

These are real gains. The composite is clearly better at preserving stage boundaries than the baseline.

## Critical reusable defect — invented decision ownership

Stage 1 introduced a `Decision Owner` column and then populated it from the person or artifact that supplied the requirement. That is a direct violation of both the benchmark rubric and the agent's own global control that activity/job title is not decision authority.

Unsupported decision-owner assignments include:

- REQ-01 -> Field Operations Coordinator;
- REQ-02 -> Field Operations Coordinator;
- REQ-04 -> Operations Support;
- REQ-06 -> Security Manager;
- REQ-07 -> `Existing-process note`;
- REQ-10 -> Product Owner;
- REQ-11 -> Product Owner.

The source establishes proposers/evidence sources, not decision authority for these requirements. This is a systematic semantic error, not a cosmetic column-label issue.

Under the rubric's **-10 each** rule for invented decision owner / approval authority / governance role, this alone exceeds the raw score and forces the final score to zero.

## Additional defects

- Overall Stage 1 readiness was not explicitly stated as **Partially Ready**.
- The explicit contractor-onboarding/security-vetting/building-owner/Change-approval constraint was moved into `CON-01` but then largely disappeared from downstream decomposition/criteria/assurance traceability.
- `AC-01-02` invented a missing-field submission-prevention rule. The source says the request records/needs the six elements, but does not establish validation behavior or a `may proceed only when` boundary.
- Manual issuance was partially reframed as a path to **record** issuance rather than preserving the sourced fallback outcome: manual temporary-access issuance remains possible when automation is unavailable.
- `TST-05` introduced a `selects the manual ... path` execution action.
- `TST-06` introduced `system logs each lifecycle event`, implying an unsupported logging mechanism.
- `ASC-01` says the verification method will be defined by Security, inventing a future governance/ownership prerequisite not established upstream.

## Additional penalties

Beyond the decision-owner penalties:

- **-5** unsupported validation/submission-prevention behavior.
- **-5** unsupported test/execution-mechanism wording (`selects` path / `logs`).
- **-10** invented future Security verification ownership/governance statement.

The final remains zero regardless of these additional penalties.

## Architecture decision

**Do not proceed to the true multi-call specialist-agent runner yet.**

The evidence does not show that the multi-agent infrastructure is warranted. The failure is first attributable to **single-call composite instruction/control**, not to an inability to pass artifacts between separate model calls: the v0.1 agent already contains the correct rule but the model violated it under combined stage load.

Create a narrowly corrected composite v0.2 and rerun Benchmark 008 Skill/Agent-only before adding infrastructure. v0.2 should:

1. prohibit a generic Decision Owner column in the requirement register;
2. permit `Decision owner` only for explicit unresolved decisions/open questions, defaulting to Unknown unless authority is sourced;
3. distinguish `Source / proposer` from `Decision owner`;
4. require all explicit process constraints to receive stable REQ/CON IDs and remain traceable through decomposition, AC/assurance and the final summary;
5. prohibit derived missing-data rejection/prevention unless the upstream rule explicitly contains an only-when/cannot/must-not boundary;
6. preserve manual fallback as an outcome, not convert it into a recording/UI mechanism;
7. remove future verification-owner/mechanism language from assurance checks.

If v0.2 fixes these issues while retaining the strong handoff structure, then a specialist-agent comparison becomes justified. If it still fails authority/status controls, the next hypothesis should be that one-call cognitive load is the limiting factor, at which point a multi-call specialist pipeline becomes a defensible experiment.
