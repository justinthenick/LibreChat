# Benchmark 001 — Skill v0.2 Results (2026-09-01)

## Test setup

Benchmark: **001 — Change Validation Automation**

Model track: **Gemini 3.6 Flash**

- Baseline: same benchmark prompt/input with no skill.
- Skill runs: same benchmark prompt/input with `$analyze-requirements` v0.2.
- Gold standard and scoring rubric were not supplied to the model.
- Two independent v0.2 skill runs were completed to check repeatability.

## Results summary

| Run | Model | Skill | Score |
|---|---|---|---:|
| Baseline | Gemini 3.6 Flash | None | 57/100 |
| Skill run 1 | Gemini 3.6 Flash | analyze-requirements v0.2 | 84/100 |
| Skill run 2 | Gemini 3.6 Flash | analyze-requirements v0.2 | 86/100 |

**Average v0.2 score:** 85/100  
**Average improvement over baseline:** +28 points

## Repeatable strengths in v0.2

- Produced a source register.
- Produced a structured requirements register with evidence class, source and confidence.
- Preserved the Change Manager vs Operations Lead enforcement disagreement rather than silently choosing a side.
- Kept the two-minute performance expectation tentative and subject to feasibility testing.
- Kept candidate integrations technically unverified.
- Separated assumptions and analyst proposals from requirements.
- Explicitly identified important items not established by the supplied evidence.
- Correctly rated the material as only partially ready for decomposition.

## Remaining recurring failure modes

### 1. Evidence provenance was confused with requirement commitment

The source explicitly says variants of:

- "should probably" start with ten common change types;
- "would like" a useful release in about six weeks;
- "two minutes feels like" the longest acceptable wait.

v0.2 correctly recognized that these statements existed in the source, but could still classify them as explicit requirements rather than distinguishing between an explicit statement and an agreed/confirmed requirement.

This exposed a missing analytical dimension: **Evidence class** answers *how the source supports the statement*, but it does not answer *how committed/agreed the requirement is*.

### 2. Decision ownership could still be invented

Both runs showed a tendency to assign unresolved governance decisions to roles such as "Executive leadership", "Change Governance" or equivalent even though the supplied evidence did not establish that decision authority.

Expected treatment: **Decision owner: Unknown** plus an open question to establish authority.

### 3. Security/governance details could be over-specified

The source says Security needs to understand what systems will be read before sign-off. Some outputs strengthened this into more detailed submission, data-field inventory or approval-process requirements that were not explicitly established.

### 4. Analyst proposals remained useful but occasionally too prescriptive

Examples included fixed trial durations, specific working groups or UI patterns. These were generally labelled as proposals, which is acceptable, but the skill should continue to prevent proposals from appearing stakeholder-approved.

## Decision

**Retain v0.2 as a material improvement over baseline and v0.1, but supersede it with v0.3 for further testing.**

v0.3 should:

1. add **Requirement status** independently of Evidence class;
2. use statuses such as Confirmed, Candidate, Target, Disputed, Deferred and Unknown;
3. explicitly prohibit invented decision owners/governance authorities;
4. require **Decision owner: Unknown** where authority is not established;
5. strengthen safeguards against over-specifying conventional security/governance process details.
